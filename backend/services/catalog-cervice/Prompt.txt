# 🚀 IMPLEMENTIERUNGSPROMPT: CATALOG-SERVICE (JAVA REST API)

## 1. Kontext / Ziel des Systems

Du implementierst einen eigenständigen **Catalog-Service** als Teil einer Microservice-Architektur für eine Handwerker-/Angebotsplattform.

Der Catalog-Service ist **zentral für alle produkt- und preisbezogenen Daten**, aber bewusst **vom User-Service entkoppelt**, da die Datenkomplexität (Preislisten, Lieferanten, Importlogiken) deutlich höher ist als klassische User- oder Stammdatenverwaltung.

### Warum dieser Service existiert

In der Domäne des Systems müssen Handwerker:

* Produkte und Materialien aus externen Quellen (z. B. Datanorm APIs) importieren
* große CSV-Preislisten verarbeiten
* eigene Produktdaten manuell pflegen
* Produkte später in Angeboten verwenden (über KI-gestützte Suche)

Diese Anforderungen führen zu:

* hoher Datenkomplexität
* vielen Integrationsquellen
* häufigen Datenänderungen
* strikter Trennung von sensiblen Preisdaten (kein direkter KI-Zugriff)

👉 Deshalb wird alles in einem dedizierten Catalog-Service gekapselt.

---

## 2. Ziel des Services

Der Catalog-Service ist eine **Java REST API**, die:

### Muss können:

1. Produkte anhand ID liefern
2. CSV-Dateien importieren und verarbeiten
3. Datanorm API Keys speichern
4. Produktdaten in einer eigenen Datenbank (`catalog-db`) speichern
5. sauber über Nginx Reverse Proxy erreichbar sein
6. als Docker Container laufen und in Docker Compose integriert sein

---

## 3. Architekturelle Rahmenbedingungen

### Service-Struktur

Der Service ist bereits vorbereitet mit folgenden Paketen:

* `sql` → Datenbankzugriff
* `openid` → Authentifizierung
* `health` → Health Checks

Du implementierst darauf aufbauend die Business-Logik.

---

### Architekturprinzipien

* REST-first Design
* Clean Architecture (Controller → Service → Repository)
* Keine direkte DB-Nutzung im Controller
* Strict separation of concerns
* Stateless API
* Kein direkter Zugriff anderer Services auf DB
* Alle Kommunikation über REST

---

## 4. Funktionale Anforderungen

## 4.1 Produktabfrage

### Endpoint:

```
GET /catalog/{id}
```

### Verhalten:

* nimmt interne Produkt-ID entgegen
* liefert vollständige Produktinformationen
* enthält:

  * Produktdaten
  * Kategorie
  * Lieferant
  * interne Preislisten (nur intern verarbeitet, nicht an KI weitergeben)

---

## 4.2 CSV Import

### Endpoint:

```
POST /catalog/import/csv
```

### Verhalten:

* nimmt CSV-Datei als Upload entgegen
* validiert Struktur
* mapped Daten in internes Produktmodell
* speichert Daten in `catalog-db`
* speichert Import-Log
* gibt Importstatus zurück:

  * Anzahl importierter Datensätze
  * Fehlerliste (falls vorhanden)

### Wichtig:

* große Dateien möglich → Streaming oder chunked processing bevorzugt
* fehlerhafte Zeilen dürfen nicht gesamten Import abbrechen

---

## 4.3 Datanorm API Key Speicherung

### Endpoint:

```
POST /catalog/config/datanorm
```

### Verhalten:

* speichert API Key für externe Datanorm Integration
* Key muss sicher gespeichert werden (Encryption at rest oder DB encrypted field)
* Key ist pro User oder Mandant gespeichert (falls vorhanden)
* Validierung: kein leerer oder ungültiger Key

---

## 5. Datenbank (catalog-db)

### Enthält:

* products
* categories
* suppliers
* price_lists
* import_logs
* datanorm_config

---

## 6. Sicherheitsanforderungen

* OpenID Authentication aktiv
* alle Endpunkte geschützt außer ggf. Health Check
* API-Key Endpoint nur für autorisierte Nutzer
* kein Leaken von Lieferantenpreisen an externe Systeme (wichtig für spätere KI-Integration)

---

## 7. Nginx Reverse Proxy Integration

Der Service ist NICHT direkt öffentlich.

### Routing:

```
/catalog/* → catalog-service
```

### Anforderungen:

* korrekte Weiterleitung aller REST Requests
* Header Forwarding (Auth Tokens!)
* keine Pfadverluste

---

## 8. Docker Container

### Anforderungen:

* Java Multi-stage build
* optimiertes Runtime Image
* Service startet automatisch
* konfigurierbar über Environment Variables

---

## 9. Docker Compose Integration

Der Service muss:

* beim Start der Gesamtanwendung automatisch starten
* abhängig sein von:

  * catalog-db
  * auth service (falls vorhanden)
* im gleichen Docker Netzwerk laufen wie Nginx

---

## 10. Logging & Observability

* Structured Logging (JSON empfohlen)
* Logging für:

  * Imports
  * API Calls
  * Fehler
* Health endpoint muss DB connectivity prüfen

---

## 11. Wichtige Designentscheidung

### ⚠️ KI-Trennung (sehr wichtig)

Der Service darf:

* Produkte suchen
* Produkte liefern

Der Service darf NICHT:

* vollständige Preislisten ungefiltert an externe KI geben

👉 Preise werden nur nach Produktauswahl weitergegeben
